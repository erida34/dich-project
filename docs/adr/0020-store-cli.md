# ADR 0020 — Store CLI read boundary

Status: Accepted for the experimental Linux store-read subset.

`store ls` and `store verify` operate on an explicitly selected existing protected store. They must never initialize a missing store, accept an initialization marker, or migrate an older schema implicitly. The existing exclusive lock still protects SQLite inspection; opening an existing WAL database may require SQLite sidecars and is not an offline forensic read-only mount. Listing reports local metadata only, while verification separately checks stored bytes against local metadata and explicitly does not reauthenticate repository signatures or prove package compatibility. Verify selects an exact object identity and object kind, fails nonzero for missing or altered data, and never activates content. `--json` uses the existing schema version and explicit status.

Acceptance uses fixture-first end-to-end CLI tests for missing/uninitialized stores, metadata-only listing, invalid identity, corrupted files, JSON errors, and concurrent locking. No command may initialize state or silently upgrade the database as a side effect of inspection. Local `.deb` inspection and authenticated exact-version fetch are implemented within the limits below; live Ubuntu exact-version fetch was verified through the explicit proxy policy in ADR 0021.

`inspect FILE` is a bounded read-only examination of a local untrusted archive, not source authentication. Open only a regular file with no symlink traversal and nonblocking flags; cap input before buffering, do not extract, and clearly label output unverified and not installable. Reject FIFOs, devices, symlinks, oversized files, malformed archives and unsupported formats without executing any scripts.

An explicit `fetch --publish-tree` can stage a freshly reauthenticated cached artifact and publish its conservative data tree into an operator-provided protected store. It never activates the package or executes maintainer scripts. Output distinguishes cache state, tree publication and compatibility: an extracted tree is neither analyzed nor installable. A failure may leave a verified cache entry or recoverable store remnants and returns an error. Store initialization requires an existing protected directory and explicit opt-in.
