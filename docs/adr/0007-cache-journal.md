# ADR 0007 — Cache durability and rollback journal

Status: Accepted for the initial library-only cache on a trusted local filesystem.

Cache data is disposable but authenticity and rollback state are not. Treat the cache root as an explicitly configured local directory, open each component without following symlinks and reject unsafe ownership or group/other write permission. Do not use a network filesystem unless its locking, rename and fsync semantics are independently established. Locks are per canonical source-policy identity and held over read, validation and publication; failures or contention must be explicit.

Maintain a source rollback floor containing the latest accepted signed Release date, its digest and latest trusted wall time. Reject an older Release, different content at the same signed date, and backwards time. The source identity includes distribution, normalized URI, configured suite and architecture with unambiguous length framing. Components and signing-key configuration are deliberately excluded: reordering or narrowing an imported source or rotating its key must not reset the rollback floor. Different configured suite aliases may still create separate floors and require policy work before production. A trusted clock and protected cache root are prerequisites; deletion or rollback of the entire floor and malicious modification by the same trusted user remain outside this initial boundary.

Write staged records within the open cache directory, fsync each file, atomically rename it, and fsync the containing directory. Release envelopes, compressed indices and verified artifact blobs are stored separately; a crash after advancing the floor can leave the new metadata unavailable until it is fetched again. Staged or unreachable files may remain. Recheck content size and digest on every cache read and reverify signed metadata under current key policy and freshness requirements. A failure after rename but before directory fsync is an uncertain commit: report failure and require a fresh read before further work. Process-level failure injection covers publication boundaries, but real power-loss and network-filesystem behavior have not been tested. Cache operations use an existing explicitly supplied directory; automatic initialization and cleanup are not implemented.

A returned in-memory snapshot pin is informational and may become stale. Fetch and cache operations recheck the current floor and reauthenticate Release under the source lock rather than trusting a pin. Lock contention waits up to 500 ms and then returns `Busy`; other lock errors are reported as I/O failures. System-clock trust, suite-alias handling and recovery from deletion or rollback of the entire floor remain open risks.
