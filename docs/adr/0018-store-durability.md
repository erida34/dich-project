# ADR 0018 — Store metadata and crash consistency (work in progress)

Status: Accepted for the experimental Linux local-filesystem subset; power-loss and network-filesystem behavior remain unverified.

Use SQLite with WAL, synchronous FULL, foreign keys enabled and an explicit schema/application version, under an existing protected local store directory. Open the directory component-by-component without following symlinks; reject unsafe ownership, writable ancestors, unsafe database files or ambiguous schema. SQLite and any sidecars require a private directory, and the implementation does not claim protection from a malicious process with the same effective UID. All SQL parameters are bound, and no extension loading or package code execution is enabled.

Publication writes and fsyncs staged content, renames it without replacement under an exclusive lock, fsyncs the containing directories, and only then commits SQLite metadata. Failure after rename but before commit may leave an orphan, never a committed reference to missing bytes. Recovery must identify and safely handle orphan/staged objects; tests must inject failures around every boundary and use separate processes for locking. The current metadata schema tracks raw archives and private trees; it does not establish cross-filesystem transactions. The connection holds an exclusive advisory lock until SQLite closes, validates the schema and sidecar paths, and refuses to adopt a pre-existing empty database. SQLite opens the validated pathname with NOFOLLOW; same-UID replacement remains outside this preliminary boundary. First initialization writes and syncs a private marker before creating the database. On restart, only a recognized marker permits initialization of an otherwise empty schema; an existing store with missing database, unexpected entries or unpaired sidecars fails closed. The marker is removed and the directory synced after initialization. A partially written marker fails closed; explicit library recovery removes only a marker matching a prefix of the expected bytes when the protected store has no database or other entries, then syncs the directory. A separate explicit recovery removes only a zero-length unmarked database in an otherwise empty protected store; nonzero unmarked databases or sidecars are never automatically adopted or removed. No power-loss guarantee is claimed from process-level fault injection.

The initial implementation pins `rusqlite` 0.40.2 with bundled SQLite 3.53.2 ([upstream build notes](https://docs.rs/crate/rusqlite/0.40.2)). SQLite is a dependency boundary; a current full dependency audit is still required before release. SQLite opens a pathname after directory and file checks; this is not a defense against a malicious process with the same effective UID.

The raw archive publication prototype works as follows: under the store lock it verifies input bytes, creates a random exclusive staging file, sets mode 0400, fsyncs the file and staging directory, renames without replacement, fsyncs both directories, rechecks source authorization and commits SQLite WAL/FULL metadata. Retries compare complete manifests and bytes; a matching orphan is synced before adoption, and a mismatch fails closed. Schema v1 to v2 migration is transactional. Fault tests include abrupt process exits at multiple boundaries, but this is not a power-loss test. Staging leftovers and orphaned archives can remain after a crash; automatic cleanup remains unimplemented; explicit cleanup can remove one recognized private staged entry under the lock after checking its subtree without following links. It fsyncs modified directories; an interrupted partial cleanup can be retried. A bounded, lock-protected inventory lists staged names, unreferenced objects, missing references and unexpected entries without authenticating or deleting them.

Private staging records normalized file paths, sizes and SHA256 values computed while writing, plus directory names and its verified artifact binding. The tree publisher reopens each staged file through the held directory descriptor and checks size and SHA256 during the copy. It validates the complete tree and all file hashes again, fsyncs files and directories, renames without replacement and commits schema v3 metadata only after reauthentication. It refuses extra, missing, linked or changed entries. Files are mode 0400 and directories 0700; this is a private store convention, not hard immutability. Failure can leave staged trees or unreferenced published trees; an explicit orphan-removal operation checks both current object tables under the lock, rejects unsafe entries and removes only an unreferenced named object. This operation must be revised before adding any new reference types; it is not garbage collection. The inventory does not validate listed content. Process-failure tests do not establish power-loss durability.
